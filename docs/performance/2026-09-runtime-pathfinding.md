# 正常移动时的主线程卡顿：寻路优化

2026-09-11。基线为 `bae532caa4a66cf214da39e114e88be9d26e933b`，优化后的原始数据保存在 `output/runtime-profile/after-grid/`，可复用工具的代码快照保存在 `output/runtime-profile/final-tool/source.json` 和 `source.patch`。

## 原因与改动

第三、第四夜的浏览器回放复现了正常移动期间的长帧。第四夜的 `dailyPatrol.tick` 在重新选择巡逻区域时，连续对多个候选位置执行全图 BFS，单次最多约 891 ms；整次游戏更新最多约 903 ms。最终保险丝触发的出口巡逻点计算也会集中执行大量寻路。CPU 采样主要落在碰撞体创建、障碍物遍历和 `patrolPath` 上。

此前每次搜索都建立字符串坐标、Map、临时数组和对象，每访问一条边又扫描全部障碍物。现在把内置玩家、怪物碰撞体对应的地图栅格化，缓存通行边，并复用数值队列、父节点和访问标记数组。缓存按障碍物的实际几何值区分，开关门、门被撞开、抽屉伸缩都会使用对应的新网格；最多保留 8 份、合计 500,000 个格子。

搜索仍然使用原来的 8 像素网格、方向顺序、最近可达位置回退和终点直线检测。非对齐起点继续执行原有的逐步碰撞检查，网格边也保留原运动算法在接触边界上的浮点行为。自定义碰撞体和越界起点使用原实现。没有修改怪物速度、感知范围、刷新数量、决策时机或关卡难度。

## 测量结果

设备：Apple M5 Pro，48 GiB 内存，18 个逻辑 CPU。Chrome headless，1280 × 800，开启真实场景绘制和 CPU 采样。

同一份输入记录每次 RAF 执行一个 50 ms 固定模拟步。计时中的游戏更新不包含离线测试策略、外层状态摘要计算和异步 GPU 工作。它用于比较相同工作量的主线程尖峰，不是线上所有设备的帧率保证。

## 正确性验证

- 第三、第四夜合计 2,919 步真实绘制回放，逐步状态摘要与修改前完全一致；第六夜另有 1,284 步一致。
- `tests/patrol-grid.test.mjs` 与冻结的原寻路实现比较完整路径，包括七张地图、两个种子、两种碰撞体、开关门、抽屉几何变化、缓存淘汰、细障碍物、不可达目标和非整数起点。
- `npm test`：220 个普通测试通过，1,400 组地图通过，0 回退、949 个不同布局；两阶段合计 12.0 秒。
- `npm run build` 通过。

这些结果证明采样场景中的寻路卡顿已显著下降，并保留了回放中的游戏行为；它们不能排除其他场景或设备上的资源加载、GPU 或系统调度问题。

## 重复诊断

准备已有的难度测试输入记录（由 `npm run test:balance` 生成），启动本地 Vite，再运行：

```sh
npm run dev -- --port 5174 --strictPort
```

在另一终端指定记录和输出目录：

```sh
npm run profile:runtime -- \
  --replay output/balance/patroller-room-early/campaign-3-0-ordinary-both-key-first-reserve0-aware-route-burst-quiet-counters-search-nearby.json \
  --out output/runtime-profile/check
```

可重复传入 `--replay FILE`，各回放顺序执行。服务器地址可用 `BASE_URL` 覆盖。采样时保持游戏代码不变，不要同时执行会重导出游戏数据的构建或全量 CPU 测试，以免 Vite 热更新中断回放；测性能时也不要并行运行其他重负载任务。

工具保存逐步耗时、方法耗时、Chrome CPU profile、代码快照和 Git 差异。如果浏览器报错、代码在采样期间改变，或回放状态与原记录不同，命令失败；先处理这些差异，再解释耗时。若有意修改玩法，需要先生成新的行为基线，不能把旧记录的状态差异当成性能优化成功。
