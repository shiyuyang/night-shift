# 地图验证性能优化复盘

记录时间：2026-09-10。代码范围：`32ef2b1` → `800c81b` → `63984a2` → `6e0d900`。

这次工作的核心收益来自减少重复计算、数据转换和分配，而不是增加线程或放宽地图检查。相同 DDR5-6000、Node 26.8.1、13 worker 下，完整地图验证从 160.6 秒降到 3.80 秒，约提速 42 倍。最终 24 worker 两次测得 3.5／3.6 秒。

## 1. 固定比较口径

- 机器：9950X，16 物理核／32 SMT 线程，64 GiB 内存；最初 DDR5-4800，用户开启 EXPO 后为 DDR5-6000。
- 工作负载：种子 0–199 × 第 2–8 关，共 1,400 组。每批 14 组，固定子进程池。
- `npm test` 的普通测试与地图池串行执行，避免两个重型池争抢资源。
- 本文地图耗时不包含构建、音频打包、浏览器测试；完整 CPU 测试耗时也需与准备阶段区分。
- 每组原有断言均保留。全局约束仍是回退次数 < 6、不同布局 > 150，实际结果均为 0 回退、949 种布局。
- 多数优化阶段仅做单次完整测量；短于数秒的结果尤其容易受启动、调度和舍入影响。历史表用于定位收益量级，不是严格统计排名。
- Mac 数字由用户提供，缺少完全相同的机器状态和计数器记录，不能据此推断处理器的通用性能高低。

## 2. 哪些改动真正有效

以下除第一行外，均为 EXPO 开启后的同机 13 worker 测量。

| 阶段 | 1,400 组耗时 | 消除的成本 |
|---|---:|---|
| DDR5-4800 基线 | 190.9 s | 硬件配置基线 |
| 开启 EXPO，DDR5-6000 | 160.6 s | 访存性能改善，不能全部归因于峰值带宽 |
| 预栅格化碰撞 | 24.06 s | 每访问一个格子就遍历全部障碍物 |
| 数组化逃生 BFS | 13.43 s | 坐标字符串、哈希集合和逐步对象队列 |
| 预计算排序分数 | 8.94 s | 比较器内部反复构建障碍物数组、计算墙距和房间占用 |
| 局部位置索引 | 8.07 s | 每次“附近有无可达点”都扫描全部点 |
| 复用候选地图分析 | 6.63 s | 验证完成后再次计算同一地图的开门／关门可达区 |
| 验证内部直接使用网格 | 3.80 s | 网格 → 坐标对象 → 查询索引／寻路网格的往返转换 |

### 碰撞检查：先消除算法级重复

原 BFS 对每个候选格子遍历所有障碍物。优化后先按角色实际脚部碰撞盒标记网格，再查紧凑数组。栅格化只检查障碍物覆盖附近的格子，边缘仍执行原来的严格相交判定。

这比“换更快的循环写法”有效得多。格子与障碍物相乘的工作量被大量消除；但栅格化仍有成本，不能描述成所有输入下都无条件线性。

### 排序：比较器不能承担昂贵的数据准备

同一个点的墙距在一次排序中不变。房间占用分数在一次候选搜索中也不变。先计算分数、再排序，避免在多次比较中重复生成数组和扫描障碍物。

必须保留稳定排序、初始洗牌和随机数调用顺序，否则看似相同的排序可能改变同一种子的道具分布。

### 数据表示：优化整条路径，不只是单个容器

将 Set 换成 TypedArray 是有效的一步，但如果前后仍生成大量对象再转回数组，数据搬运依旧存在。最终收益来自让验证内部一直使用同一个紧凑网格，只在公开接口确实需要坐标列表时才创建对象。

这不是“所有对象都应该改成 TypedArray”。对低频交互、内容配置等部分保留可读的数据结构；仅压缩经过采样确认的热点工作集。

### 复用结果：先限定有效期，再谈缓存

`analyzePlayableLevel()` 产生同一候选地图的查询快照，验证和箱子接近性检查共用。地图改变后重新分析。`validatePlayableLevel()` 保持原有 `{valid, errors}` 接口。

没有添加跨关卡全局缓存，也没有只用对象身份作为缓存键。门、家具、箱子位置和停尸房抽屉都会改变碰撞几何，过期缓存会把性能优化变成“死地图”或穿墙 bug。

## 3. 正确性证据要比“测试没报错”更强

本轮保留并补充了三层验证：

1. 完整 1,400 组测试和原有全局断言。
2. 冻结原算法作为独立参照，比较完整可达点顺序、最短距离及验证错误列表。覆盖严格距离边界、负数／小数坐标、自定义脚部形状、重复点、稀疏点、封闭出生点、门和抽屉递归。
3. 第 1–8 关 × 种子 0–7，共 64 组完整关卡 JSON 的前后 SHA-256 一致：`eed4605d5ec8f8074211bf87770474ceadfa7dc60da5d60736e82133ea8a475f`。

## 4. 硬件排查中需要纠正的判断

### CPU 占用率不等于有效计算效率

最初 13、24、32 worker 的地图耗时几乎相同。增加线程会增加共享资源竞争、调度及累计执行周期，并不保证缩短完成时间。

后期只使用互不共享 SMT 的物理核心、尽量均匀分配到两组 L3，8／13／16 worker 两轮分别为 9.6／8.2／8.1 秒。这排除了“仅仅因为开了 SMT”这一单一解释，但仍不足以定位具体硬件瓶颈。该组数据属于中间版本，不是最终 3.8 秒版本。

### 访存受限不等于 DDR5 总线跑满

核心侧 `DRAM→L2 填充次数 × 64` 是部分读取流量估算。最初约 28 GB/s 的平台值没有包含全部写入；据此称“DDR5 上限只有 28 GB/s”是错误的。

后来临时加载系统已有的 `amd_uncore` 驱动，才暴露两个 UMC 计数器。此前应说“接口尚未加载”，不能断言“内核没有支持”。测试结束后卸载，未写入持久配置。

控制器实测如下，均为系统级计数，包含约 0.59 GB/s 的空闲背景流量；每组事件调度覆盖率 100%。这些同样是中间版本数据。

| 负载 | 读取 GB/s | 写入 GB/s | 总计 GB/s | 平均数据总线占用 |
|---|---:|---:|---:|---:|
| 地图／8 物理核 | 24.62 | 22.65 | 47.28 | 49.3% |
| 地图／13 物理核 | 29.41 | 26.90 | 56.31 | 58.8% |
| 地图／16 物理核 | 29.75 | 26.94 | 56.69 | 59.2% |
| STREAM／13 物理核 | 42.58 | 19.11 | 61.69 | 64.4% |

两个控制器的 MEMCLK 约 2.994 GHz，与 DDR5-6000 一致；这不是 UCLK 或 FCLK 测量。总线平均占用约 59% 不支持“理论线速已耗尽”，也不能排除行切换、读写切换、控制器调度、访问依赖或内部传输造成的访存瓶颈。

### STREAM、核心读计数和理论带宽不能混算

- 双通道 DDR5-6000 的理论峰值：6,000 MT/s × 8 字节 × 2 = 96 GB/s。
- STREAM：按算法所需读＋写字节计数，报告有效带宽。标准输出取预热后最快一次，不能称为整段运行平均值。
- 核心 PMU：统计该事件覆盖的缓存填充。
- UMC：从读写 CAS 命令计数估算控制器流量；总线占用来自时钟事件。

STREAM 使用官方原版 C 源码，GCC 16.2.1，`-O3 -march=native -fopenmp`，每个数组 512 MiB、总计 1.5 GiB、20 次迭代，8／13／16 个物理线程各两轮，均通过数值校验。Copy 有效带宽约 62–64 GB/s，Triad 约 46–47 GB/s。不能把这些数字与 UMC 的整段均值直接相除算利用率。

### 等待占比下降不是唯一目标

`ex_no_retire.load_not_complete` 表示最老指令因读取未完成而无法退休的周期，并非 CPU 完全停止，也不能直接换算为墙钟等待秒数。

局部索引阶段曾出现“总耗时下降，但累计等待周期上升”。它仍可能是有效优化，因为总工作减少。应同时报告绝对周期、占比、总流量和耗时，不只选择看起来更好的指标。

EXPO 的约 16% 耗时收益是真实的，但发生在旧算法上。最新代码大幅改变访问模式后，不能直接套用同一个收益比例。

## 5. 下次可直接复用的工作方法

1. 固定提交、Node、输入规模、worker 数和计时边界。记录内存配置、物理核／SMT、可用资源及背景负载。
2. 用完整用例建立基线。保留少量、固定的快速子集定位热点，但不拿子集替代全量验收。
3. 先采样热点，优先检查嵌套扫描、排序比较器、重复遍历和数据表示转换。
4. 一次解决一个明确成本，保持接口和行为契约；先用独立参考实现做差分，再跑完整测试。
5. 比较总耗时、CPU 时间／周期、指令数、GC 与必要的硬件计数器。明确采样百分比与精确计数的区别。
6. 只有证据指向访存时才扩大硬件诊断。检查现有驱动和 PMU 支持；读取系统级计数需要相应权限，结束后清理临时状态。
7. 每次较大算法改动后重新测并行度。旧版本的最佳 worker 数不能当永久结论。
8. 保存最终配置、结果和局限。提交、部署状态与“本地测过”分开记录。

推荐验收命令仍使用项目既有入口：

```sh
TEST_WORKERS=13 npm test
npm run test:layouts -- --workers 24
npx tsc --noEmit
```

不要为跑分减少种子、不再检查抽屉、不验证失败路径，或提前返回并改变公开错误列表。不要在完整测试运行器中再嵌套一个独立定额的重型池。

## 6. 最终并行度与跨平台对比

最终版本 `6e0d900`：

| worker | 第一次 | 第二次 |
|---|---:|---:|
| 13 | 3.80 s | 未重复 |
| 16 | 3.6 s | 3.6 s |
| 24 | 3.5 s | 3.6 s |
| 32 | 3.7 s | 3.7 s |

保留现有默认预算（本机通常为 24）即可，不将 24 硬编码为所有设备的最佳值。用户报告同版本 M5 Pro、13 worker 为 3.78 秒，与本机 3.80 秒的差异不足以判断胜负。

## 7. 对游戏与后续开发的意义

优化的是共享地图生成／验证代码，不只是测试壳，因此有助于减少生成和切关计算。但 1,400 张地图的提速不能直接换算成游戏 FPS 或语言切换速度。

主界面切语言调用 `window.location.reload()` 是独立问题，本轮未修改。渲染、实时怪物寻路、音频与网络延迟也需要各自的浏览器测量。

后续仍可研究开门／关门共用基础碰撞栅格、有限生命周期内复用工作数组，以及 worker 启动和尾批不均衡。不过在约 3.5 秒总时长下，应先测量占比；不为小幅、不稳定的收益引入全局缓存或复杂并发框架。
